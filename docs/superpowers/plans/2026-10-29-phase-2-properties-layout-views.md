# Phase 2: Property Engine, Hybrid Layout and Private Saved Views Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Staff work leads in a Twenty-style layout with the CRM's colours, filter, sort and pick columns by any property the site defines (built-in or custom), add a custom property without a developer, and keep private saved views.

**Architecture:** One **property catalogue per site** replaces the code-only catalogue of PR #1: the built-ins stay in `leadPropertyCatalog` (code), a site may relabel or hide them through a row in the new `app.properties` table, and custom properties are further rows there with their values in a new `leads.custom_values` JSONB column (no DDL at runtime, keys permanent, deleted keys reserved by a tombstone). Every list, board, filter, sort, column, layout and record screen resolves properties through the same `PropertyCatalog` object, built once per request from those rows. A **layout** per site and lead type orders sections and property keys (`app.property_layouts`). **Private saved views** (`app.saved_views`, owner-scoped row security) hold the inbox state minus the free-text search. The admin gets Canadian Plans' view bar, menus and side panel, restyled light with the CRM red, a 220 px sidebar and 32 px rows; the lead record is rendered from the layout and opens in a side panel from the list. The tables carry an `object` column (`lead` now, `plan` in phase 3) so plans reuse the engine without new tables.

**Tech Stack:** TypeScript (strict), Next.js 16 + React 19 + Tailwind 4 + shadcn (radix-ui 1.6.7), Zod 4, Express 5, Drizzle + PostgreSQL 17 (JSONB, advisory locks, RLS), Vitest 5, Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-28-merge-canadian-plans-design.md` §2 (decisions 10, 16, 23, 24), §5.1–§5.3, §11, §12 phase 2, §13, §14. Value rules for `parsePropertyValue` (the spec's kinds): `text` ≤ `maxLength` (default 200) trimmed, non-empty; `longText` ≤ 4000; `number` finite, |x| ≤ 1e12; `money` an integer number of cents, |x| ≤ 1e12; `count` integer 0–10000; `date` a real calendar day `YYYY-MM-DD` (`isCalendarDate`); `dateTime` ISO date-time; `yesNo` boolean; `choice` one of the non-hidden option values (a hidden option is accepted only when it equals the current stored value, which the caller checks); `email` lower-cased, `z.email()`, ≤ 254; `phone` after stripping `[ ()-]` matches `^\+?[0-9]{5,20}$`; `url` `http(s)` only, ≤ 2048. Empty string is `{ ok: false }` (callers clear with `null`). `formatPropertyValue`: `money` → `Intl.NumberFormat('en-CA', { style: 'currency', currency: 'CAD' })` of cents/100; `yesNo` → `Yes`/`No`; `choice` → the option label; `date`/`dateTime` → `en-CA` medium date; the rest → the string.

Operators: `leadPropertyOperators(kind)` adds `number` and `money` with the `count` set, and `email`, `phone`, `url` with the `text` set. `leadPropertyFilterValueSchema`'s number branch becomes `z.number().finite().min(-1e12).max(1e12)`; `isValidLeadPropertyFilter` keeps `count` at integers 0–10000 and requires an integer for `money`.

Catalogue resolution in `buildPropertyCatalog`: a built-in row (`origin: 'builtin'`) overrides only `label` and `hidden` of the code definition; a custom row is a `SiteProperty` with `storage: 'custom'`, `editable: true`; `forType(t)` = the type's `leadTypeProperties` uses (resolved as today, hidden removed) followed by custom properties whose `leadTypes` is empty or includes `t`, by `position` then `key`; `filterable()` reuses PR #1's merge-across-types logic over `all` minus hidden minus sensitive.
